\section{Approach}\label{sec:Approach}

This section presents our approach to detecting missing \texttt{RB\_GC\_GUARD} directives. We first discuss our choice of analysis framework and the rationale for selecting CodeQL (Section~\ref{sec:tool_selection}). We then describe the detection algorithm and its key predicates (Section~\ref{sec:detection_algorithm}). Finally, we detail the implementation of each analysis component (Section~\ref{sec:implementation}).

\subsection{Tool Selection}\label{sec:tool_selection}

Given the requirements outlined in Section~\ref{sec:Requirements}, we considered several approaches for implementing the static analysis. The ideal tool must support efficient querying over a large codebase, provide access to both syntactic (AST) and semantic (control-flow, type) information, enable recursive queries for computing transitive closures, and allow declarative specification of complex patterns. As discussed in Section~\ref{sec:Requirements}, requirements R1 (recursive call-graph reachability), R3 (ownership binding tracking), and R4 (multi-entity control-flow ordering) are particularly challenging and strongly influence tool selection.

\subsubsection*{Alternative Approaches and Their Limitations.}
We evaluated several categories of static analysis tools before selecting our implementation platform.

\emph{Semantic pattern-matching tools} such as Coccinelle~\cite{UgawaFujimoto2019PRO} excel at matching code patterns against syntax, semantics, and control flow. Coccinelle is widely used in Linux kernel development for API evolution and defect detection. However, Coccinelle does not track state automatically across the program and lacks built-in support for computing call-graph reachability. While limited state tracking can be added through Python or OCaml snippets, implementing recursive transitive closure computation (required for R1) would require substantial custom infrastructure. Furthermore, Coccinelle's design focuses on local pattern matching rather than the multi-entity relational queries needed for R3 and R4.

\emph{Compiler-integrated analyzers} such as the Clang Static Analyzer provide rich semantic information through path-sensitive, interprocedural analysis based on symbolic execution. The Clang Static Analyzer constructs an ``exploded graph'' that tracks program state along execution paths, making it effective for detecting bugs like null pointer dereferences and use-after-free. However, this approach faces scalability challenges for whole-program analysis: the state space can grow exponentially, and the analyzer typically bounds exploration depth to remain tractable. More fundamentally, the Clang Static Analyzer is designed around specific bug patterns with custom checkers, rather than declarative queries over program structure. Implementing our analysis would require writing a custom checker in C++ that manually manages the state machine for tracking ownership bindings across control-flow paths---a significant engineering effort compared to a declarative specification.

\emph{GCC's static analyzer} (\texttt{-fanalyzer}) similarly provides interprocedural data-flow analysis but lacks extension mechanisms for custom analyses. It is designed to detect specific vulnerability classes rather than arbitrary user-defined patterns.

\emph{Custom analyzers} written in general-purpose languages offer maximum flexibility but require substantial engineering effort to parse C code (including macro handling), construct control-flow graphs, implement efficient indexing, and develop query evaluation strategies. For a research prototype, this overhead would detract from the core contribution.

\subsubsection*{CodeQL as the Implementation Platform.}
CodeQL is a declarative program analysis framework that allows users to write custom queries over source code~\cite{codeql_about}. It first compiles source code into a relational database, then evaluates user-defined queries written in a Datalog-inspired language called QL. We selected CodeQL because its design directly addresses the challenging requirements.

First, CodeQL represents source code as a queryable relational database, with pre-computed indices over types, names, and structural properties~\cite{ql_ecoop}. This enables efficient lookups that avoid the need for full enumeration, addressing the scale challenge of CRuby's 300,000+ lines of code.

Second, the QL language supports recursive predicates~\cite{codeql_recursion}, which is essential for computing transitive call-graph reachability (R1). CodeQL's query engine implements efficient fixed-point computation with memoization, allowing us to express the GC-trigger analysis declaratively while the engine handles the recursive evaluation.

Third, CodeQL's relational model naturally expresses the ownership binding between subordinate pointers and \texttt{VALUE} variables (R3). We can define predicates that relate derivation sites, pointer variables, and owning \texttt{VALUE}s, then join these relations with control-flow information to detect hazardous patterns.

Fourth, CodeQL provides built-in support for C/C++ control-flow analysis, including \texttt{getASuccessor} and \texttt{getAPredecessor} relations over control-flow nodes. This enables the multi-entity ordering analysis required by R4 without implementing control-flow graph construction from scratch.

Fifth, CodeQL's AST representation of preprocessed code allows detection of \texttt{RB\_GC\_GUARD} usage (R5) by recognizing the characteristic expansion pattern---specifically, the declaration of a local variable named \texttt{rb\_gc\_guarded\_ptr}.

\subsection{Query Implementation}\label{sec:detection_algorithm}

Our detection algorithm implements the requirements from Section~\ref{sec:Requirements} as a conjunction of predicates over the CodeQL database. The core detection pattern can be expressed as an ordering constraint over control-flow paths:

\[
\textsc{Derivation}(p \leftarrow v) \xrightarrow{CFG^*} \textsc{LastUse}(v) \xrightarrow{CFG^+} \textsc{Trigger} \xrightarrow{CFG^+} \textsc{Use}(p)
\]

where $\xrightarrow{CFG^*}$ denotes zero or more control-flow steps and $\xrightarrow{CFG^+}$ denotes one or more steps. The constraint captures that the last \texttt{VALUE}-level use of $v$ must precede the trigger, which in turn must precede the use of $p$.

Listing~\ref{lst:running_example} illustrates a buggy pattern. The local variable \texttt{str} is used to derive a pointer \texttt{ptr} on line 3. The last \texttt{VALUE}-level access to \texttt{str} occurs on line 4 via \texttt{RSTRING\_LEN}. A GC-triggering call occurs on line 6 (\texttt{rb\_str\_new}), after which \texttt{ptr} is used on line 8. Because \texttt{str} has no access after the trigger and no explicit guard, an optimizing compiler may treat \texttt{str} as dead at line 6, potentially causing \texttt{ptr} to become a dangling pointer.

\begin{figure}[tb]
\begin{lstlisting}[caption={A buggy example.},label={lst:running_example}]
static VALUE process_data(VALUE input) {
    VALUE str = rb_funcall(input, rb_intern("to_s"), 0);
    char *ptr = RSTRING_PTR(str);     // derivation
    size_t len = RSTRING_LEN(str);    // last VALUE-level use

    VALUE result = rb_str_new(0, len * 2);  // GC trigger

    memcpy(RSTRING_PTR(result), ptr, len);  // use of ptr
    return result;
}
\end{lstlisting}
\end{figure}

The query's logic can be split into four phases. In the first phase, we identify all local variables of type \texttt{VALUE}. In the second phase, for each \texttt{VALUE} variable, we find derivation sites where a raw pointer is derived. In the third phase, we compute the set of functions that may transitively trigger GC via call-graph reachability. In the fourth phase, we check control-flow ordering constraints to identify variables that need guards but lack them.

\subsubsection*{Identifying VALUE Variables and Pointer Derivations}
The foundation of our analysis is identifying local variables of type \texttt{VALUE} and tracking their relationship to derived pointers. We define a CodeQL class \texttt{ValueVariable} that matches local variables whose type is \texttt{VALUE} (handling both direct declarations and typedef indirections). Defining specific types in this manner limits the upper bound on the size of a relation, helping the query optimizer be more effective~\cite{codeql_specific_types}.

For pointer derivations, we define predicates that recognize common derivation operations in CRuby by matching against function names such as \texttt{RSTRING\_PTR}, \texttt{RARRAY\_PTR}, and \texttt{TypedData\_Get\_Struct}. The logical binding between owning objects and subordinate pointers is established when: (1) an owning object (\texttt{VALUE}) is passed to a pointer derivation function call, (2) the return value is assigned to a pointer-type variable, and (3) the assigned pointer is considered a subordinate pointer of that owning object.

\subsubsection*{GC Triggering Functions}
We identify GC-triggering functions through transitive reachability to CRuby's GC entry point \texttt{gc\_enter}. This is achieved using CodeQL's recursive predicate capability~\cite{codeql_recursion}. Listing~\ref{lst:is_gc_trigger} shows the implementation.

\begin{figure}[tb]
\begin{lstlisting}[caption={CodeQL predicate for GC trigger detection via call-graph reachability.},label={lst:is_gc_trigger}]
predicate isGcTrigger(Function function) {
  exists(Expr s, Call call |
    s = function.getAPredecessor*() and
    s instanceof FunctionCall and
    s.getAChild*() = call and
    (call.getTarget().getName() = "gc_enter" or
     isGcTrigger(call.getTarget()))
  )
}

class GcTriggerCall extends FunctionCall {
  GcTriggerCall() {
    isGcTrigger(this.getTarget())
  }
}
\end{lstlisting}
\end{figure}

This predicate determines whether the GC entry point \texttt{gc\_enter} is reachable from a function. It recursively checks if the function's body, or the body of any called function, contains an invocation of \texttt{gc\_enter}. The result is cached after the first execution, enabling subsequent queries to reuse the computed trigger set.

\subsubsection*{Detecting Existing Guards}
GuardLint detects \texttt{RB\_GC\_GUARD} usage through recognizing the characteristic expansion pattern of the GCC-style implementation: the introduction of a local temporary named \texttt{rb\_gc\_guarded\_ptr} initialized with the address of the guarded \texttt{VALUE}.

\begin{figure}[tb]
\begin{lstlisting}[caption={CodeQL predicate for detecting existing guards.},label={lst:guard_detection}]
predicate hasGuard(ValueVariable v) {
  exists(VariableDeclarationEntry decl |
    decl.getVariable()
        .getInitializer()
        .getExpr()
        .(AddressOfExpr)
        .getAnOperand()
        .(VariableAccess)
        .getTarget() = v and
    decl.getVariable().getName() = "rb_gc_guarded_ptr"
  )
}
\end{lstlisting}
\end{figure}

\subsubsection*{Control-Flow Ordering Analysis}
The core detection logic combines the above components with control-flow ordering constraints. Listing~\ref{lst:needs_guard} shows the \texttt{needsGuard} predicate that captures the hazardous pattern.

\begin{figure}[tb]
\begin{lstlisting}[caption={CodeQL predicate for detecting variables that need guards.},label={lst:needs_guard}]
predicate needsGuard(
  ValueVariable v, PointerVariable subordinatePointer,
  GcTriggerCall gtc, PointerVariableAccess pointerUsageAccess,
  ControlFlowNode derivationSite
) {
  gtc.getControlFlowScope() = v.getParentScope*().(Function) and
  gtc.getControlFlowScope() = derivationSite.getControlFlowScope() and
  subordinatePointer != v and
  pointerUsageAccess.getTarget() = subordinatePointer and
  gtc.getASuccessor+() = pointerUsageAccess and
  not exists(VariableAccess va |
    va.getTarget() = v and
    va = gtc.getASuccessor+() and
    not isGuardAccess(va)
  ) and
  hasSubordinatePointerDerivation(v, subordinatePointer, derivationSite)
}
\end{lstlisting}
\end{figure}

The predicate checks that: (1) the GC trigger and derivation site are in the same function scope as the \texttt{VALUE} variable, (2) the subordinate pointer is accessed after the GC trigger (via \texttt{getASuccessor+}), (3) there is no \texttt{VALUE}-level access after the trigger (excluding guard accesses), and (4) the subordinate pointer was derived from the \texttt{VALUE} variable.

\subsubsection*{Main Query Structure}
The main query structure combines these components. Listing~\ref{lst:missing_guard_ql} shows the missing guard detection query.

\begin{figure}[tb]
\begin{lstlisting}[caption={Main query for detecting omitted guards.},label={lst:missing_guard_ql}]
from ValueVariable v, PointerVariable p, GcTriggerCall gtc,
     PointerVariableAccess pointerUsageAccess, PointerDerivationAction derivationSite
where
  needsGuard(v, p, gtc, pointerUsageAccess, derivationSite) and not hasGuard(v)
select v, derivationSite, gtc, pointerUsageAccess

\end{lstlisting}
\end{figure}

Because the CFG represents one possible evaluation order out of those allowed by the C language specification and compiler, the analysis remains a conservative approximation rather than a compiler-precise liveness proof. Additionally, we conservatively treat passing a subordinate pointer as an argument as a potential use, though we do not fully analyze derived-pointer dereferences inside callees in the current configuration.

\subsubsection*{Complementary Queries}
In addition to the missing-guard query, GuardLint includes queries to identify \emph{matched guards} (existing \texttt{RB\_GC\_GUARD} invocations where the guarded variable satisfies \texttt{needsGuard}, representing guards that our model confirms as necessary) and \emph{potentially redundant guards} (existing guards where the guarded variable does \emph{not} satisfy \texttt{needsGuard}, which may be candidates for removal, though they could also represent defensive coding or protection against future code changes). These complementary queries support a practical workflow: developers can review matched guards for confidence, investigate missing guards for safety, and consider removing redundant guards for performance and clearance.
