\title{GuardLint: Static Analysis of CRuby\\
for Checking GC Guards}

\begin{abstract}
The reference implementation of the Ruby programming language (CRuby) employs a conservative garbage collector (GC). To ensure memory safety in its C implementation, developers must explicitly insert \texttt{RB\_GC\_GUARD} macros to prevent the compiler from optimizing away stack variables that anchor live objects. Omitting these guards leads to use-after-free bugs and interpreter crashes, while excessive use can degrade runtime performance. In practice, identifying the correct placement of these guards is error-prone, and numerous omissions have historically been discovered in CRuby.

This paper presents GuardLint, a static analyzer designed to detect omissions of \texttt{RB\_GC\_GUARD}. Implemented as a set of CodeQL queries, GuardLint models the temporal lifecycle of object pointers to identify unsafe usage patterns. We applied GuardLint to the CRuby codebase. Our analysis identified 32 instances where guards are correctly placed and necessary. Furthermore, we identified 267 instances of potentially redundant guards and 236 instances of potential guard omissions. Through manual verification of the flagged omissions, we confirmed one highly probable bug in the OpenSSL extension. Additionally, we demonstrated that a naive strategy of guarding all variables results in a significant performance penalty, justifying the need for precise static analysis.
\end{abstract}

\section{Introduction}
Many programming languages with automatic memory management (so-called \emph{garbage-collected languages}) are implemented in unsafe languages such as C and C++. Those implementations have to carefully manipulate the pointers so that garbage collectors correctly recognize used and unused memory areas.

CRuby\footnote{\url{https://github.com/ruby/ruby}}, which is the most widely used Ruby implementation, is implemented in C. CRuby requires its implementation to add a macro called \texttt{RB\_GC\_GUARD} under a certain condition that ensures validity of the pointers. However, it is easy to forget to insert the guard macro calls, which in fact resulted in many memory bugs. The authors believe that there are still many uncovered bugs.

In the CRuby implementation, including both the interpreter core and its C extensions, variables of type \texttt{VALUE} to represent Ruby objects. CRuby's conservative garbage collector~\cite{gchandbook} does not require the implementation to explicitly inform the object references of the GC since it automatically takes the C stack and the registers as GC root. Compiler optimizations can overwrite the registers that references Ruby objects after the last use. This causes the GC to reclaim objects that still look to be referenced by a variable at the source code level. A critical memory bug arises when the C code extracts a pointer to a subordinate memory area of an object. A subordinate memory area is raw C memory area owned by a Ruby object but not itself a Ruby object. For example, a String's byte buffer or an Array's contiguous element storage. This memory is allocated and reclaimed together with its owning object by the garbage collector. And a subordinate pointer is a raw C pointer that points into such an area, typically obtained via accessor macros such as \texttt{RSTRING\_PTR} or \texttt{RARRAY\_PTR}. The garbage collector deallocates the object while extracted pointer remains in use, which means a use-after-free bug.

CRuby provides a macro named \texttt{RB\_GC\_GUARD} to ensure that \texttt{VALUE} variables remain on the stack, preventing them from being prematurely collected.  

Missing guards cause crashes. But correct placement is challenging. Developers must identify where extracted pointers might be accessed after garbage collection triggers, which we call \textbf{The Guard Problem}.

This paper presents a CodeQL-based static analysis to automatically detect missing \texttt{RB\_GC\_GUARD} calls.
Our approach consists of (1) defining the conditions when a \texttt{VALUE} variable should be protected by \texttt{RB\_GC\_GUARD} and (2) implementing a static analyzer in CodeQL that checks these conditions.

The remainder of this paper is organized as follows. Section~\ref{sec:Background} provides background and characterizes the Guard Problem. Section~\ref{sec:Approach} describes our implementation of static analysis. Section~\ref{sec:Experiment} reports the analysis results with respect to the CRuby codebase and discusses our findings. Section~\ref{sec:Discussion} analyzes the capabilities and limitations of our current implementation. Section~\ref{sec:Related} reviews related work. Finally, Section~\ref{sec:Conclusion} concludes the paper and outlines directions for future work.

\section{Background}\label{sec:Background}
\subsection*{Memory Organization in CRuby}

In CRuby, some objects have a subordinate memory area which is a non-Ruby object data, retrieved by a pointer from a Ruby object, and becomes invalid when the parent object is reclaimed by the garbage collector. For instance, the body of a String object is a subordinate memroy area, as it is allocated outside of the object heap and is deallocated when the string object is garbage collected. 

\subsection*{Accessing Subordinate Memory}

CRuby provides accessor macros such as \texttt{RSTRING\_PTR} and \texttt{RARRAY\_PTR} to extract raw C pointers to these subordinate areas:

\begin{figure}[tb]
\begin{lstlisting}[caption={Accessing subordinate memory}]
VALUE str = rb_str_new_cstr("Hello");
char *ptr = RSTRING_PTR(str);  
// extract pointer to string data
\end{lstlisting}
\end{figure}

Subordinate pointers remain valid only while their parent object lives. If the garbage collector determines the parent is unreachable, it deallocates both the object and its subordinate memory, leaving any extracted pointers dangling. The critical requirement is that parent objects must remain reachable throughout subordinate pointer usage.

\subsection*{Compiler Optimizations}

C compilers may allocate a C variable to a register and reuse the register or reuse the stack slot *** for another variable when the first variable is no longer accessed. For example, in the following code fragment, compiled code of the str would be allocated in register, and then another variable may be allocated in the same register at line 5.

\begin{figure}[tb]
\begin{lstlisting}[caption={Compiler optimization example}]
VALUE str = rb_str_new_cstr("data");
char *ptr = RSTRING_PTR(str);
// Compiler may eliminate str
// from stack/registers here
VALUE new_str = rb_str_new_cstr("new data");
process_data(ptr);  
// str invisible to GC
\end{lstlisting}
\end{figure}

This optimization is valid from the C perspective but does not cooperate well with CRuby's conservative garbage collector, which relies on scanning the stack and registers to find live objects. When the compiler overwrites a register that store an object reference, the GC cannot detect that the object is still needed for accessing its subordinate pointers.

\subsection*{Conservative GC and the Guard}

CRuby uses a conservative garbage collector~\cite{ruby_conservative} which identifies live objects by scanning the C stack and registers. To prevent compiler optimizations from overwriting registers, CRuby provides the \texttt{RB\_GC\_GUARD} macro, which creates a volatile reference ensuring that the variable remains visible to the garbage collector. The implementation of the macro in CRuby version 3.4.5 is listed in Listing~\ref{lst:rbgcguard}.

\begin{figure}[tb]
\begin{lstlisting}[caption={RB\_GC\_GUARD (Simplified GCC Ver.)},label={lst:rbgcguard}]
#ifdef __GNUC__
#define RB_GC_GUARD(v) \
    (*__extension__ ({ \
        volatile VALUE *rb_gc_guarded_ptr = &(v); \
        __asm__("" : : "m"(rb_gc_guarded_ptr)); \
        rb_gc_guarded_ptr; \
    }))
// ... (MSC_VER implementation omitted)
#endif
\end{lstlisting}
\end{figure}

\subsection{The Guard Problem}

We identify a specific class of memory safety problem in CRuby's C implementation that we term \textbf{The Guard Problem}. This occurs when the C code uses a pointer that points to a subordinate memory area within garbage-collected objects.

Consider this code fragment:
\begin{figure}[tb]
\begin{lstlisting}[caption={The Guard Problem}]
VALUE str = rb_str_new_cstr("Hello");
char *ptr = RSTRING_PTR(str);
rb_ary_push(array, other_value); // GC trigger?
printf("%s\n", ptr); // Use after potential GC
\end{lstlisting}
\end{figure}

The compiler may allocate str in a register and overwrites the register by another local variable before executing line 3. Because the String object is not referenced from any registers or the stack, and when GC runs inside of rb\_ary\_push, the String object is reclaimed.

Manual \texttt{RB\_GC\_GUARD} placement is error-prone because developers must (1) identify all locations where subordinate pointers are extracted, (2) locate potential GC trigger points, (3) ensure guards cover the entire lifetime of pointer usage. The complexity of the condition when the guard is needed and the subtlety of GC make this a frequent source of bugs. Furthermore, as GC will not start a lot of the time when a GC trigger is called, it is hard to reproduce and debug this kind of bug. Although there are static analysis frameworks for detecting use-after-free bugs in traditional C++~\cite{static_analysis_use_after_free_cpp}\cite{spatio_temporal_context_reduction}\cite{static_analysis_dangling_pointer}, The Guard Problem presents unique challenges specific to conservative garbage collection environments.

\section{Approach}\label{sec:Approach}

\subsection{CodeQL for Static Analysis}

CodeQL is a code analysis platform that derivates source code into a relational database representation. CodeQL uses QL, a declarative query language based on Datalog, to express program analysis logic through predicates and recursive queries.

CodeQL's database derivation captures semantic information including abstract syntax trees, control flow graphs, data flow relationships, and type hierarchies. This supports interprocedural analysis for tracking VALUE objects and their derivated pointers across function boundaries in CRuby's C codebase.

\begin{figure}[tb]
\begin{lstlisting}[language=java, caption={Predicate for GC trigger detection}, label={lst:ql_trigger}]
predicate isGcTrigger(Function function) {
  exists(Expr s, Call call |
    s.getEnclosingFunction() = function and
    s.getAChild*() = call and
    (call.getTarget().getName() = "gc_enter" 
      or isGcTrigger(call.getTarget()))
  )
}
\end{lstlisting}
\end{figure}

\subsection{Static Analysis Approach Overview}
We model the main problematic patterns and implement both intraprocedural and interprocedural analysis to track pointer lifetimes across function boundaries.

\subsection{Problematic Pattern Classification}

Our analysis detects problematic patterns across different syntactic forms of pointer derivation. We removed irrelevant code from original source files for clarity.

\textbf{1. Declaration Pattern:} Pointer derivation occurs directly during variable declaration (see Listing \ref{lst:decl_pattern}).

\begin{figure}[tb]
\begin{lstlisting}[caption={Declaration Pattern (time.c)}, label={lst:decl_pattern}]
if (rb_typeddata_is_kind_of(time, &time_data_type)) {
    // 1. Derivation
    struct time_object *tobj = RTYPEDDATA_GET_DATA(time);

    // 2. Trigger (potentially)
    time_gmtime(time); 
    
    // 3. Usage
    t = rb_time_unmagnify(tobj->timew);

    RB_GC_GUARD(time);
}
\end{lstlisting}
\end{figure}

\textbf{2. Initialized Later Pattern:} The pointer is declared first but initialized with a derivation value later. This separation often obscures the lifetime dependency.

\begin{figure}[tb]
\begin{lstlisting}[caption={Initialized Later Pattern}, label={lst:init_later}]
VALUE path = rb_str_new_cstr("path");
char *p;
// ... complex logic ...
p = RSTRING_PTR(path); // 1. Derivation
// ... more logic ...
rb_gc(); // 2. Trigger
printf("%s", p); // 3. Usage (Unsafe!)
RB_GC_GUARD(path); 
\end{lstlisting}
\end{figure}

\textbf{3. Interprocedural Pattern:} Derivated pointers are passed to other functions, making the usage site distinct from the derivation site.

\begin{figure}[tb]
\begin{lstlisting}[caption={Interprocedural Pattern (digest.c)}, label={lst:interproc_pattern}]
static VALUE
rb_digest_base_update(VALUE self, VALUE str)
{
    void *pctx;
    // ... setup ...
    StringValue(str);
    // pctx usage may trigger GC
    algo->update_func(pctx, 
        (unsigned char *)RSTRING_PTR(str), // Deriv.
        RSTRING_LEN(str));
    RB_GC_GUARD(str);
    return self;
}
\end{lstlisting}
\end{figure}

\subsection{GC Trigger Detection}

We implement recursive call analysis to detect both direct and indirect GC triggers. It is done by analyze the call graph to identify functions that eventually call GC entry points.

\subsection{Interprocedural Pointer Usage Analysis}

We implement an \texttt{isArgumentNotSafe} predicate that performs interprocedural analysis to determine if  function arguments might be used unsafely. 

\subsection{Control-flow Analysis}

Control-flow analysis is essential for matching the problematic code pattern where derivated pointers are used after GC triggers. Our approach must verify that pointer derivation precedes GC triggers, which precede pointer usage, along feasible execution paths.

CodeQL's control flow graph (CFG) analysis enables determination of operation ordering to detect code matching the following execution order:

1. A certain \texttt{VALUE} variable's last reference
2. GC triggers
3. Usage of pointers pointing to the subordinate memory area 

\section{Experiment}\label{sec:Experiment}
We evaluated our approach on CRuby version 3.4.5's core codebase which contains 339,617 lines of C code calculated by \texttt{scc}\footnote{\url{https://github.com/boyter/scc}} command.

For the purpose of evaluation, we utilize the existing \texttt{RB\_GC\_GUARD} placements in the codebase as a baseline. We categorize a guard as ``Good'' (Correct) if our tool identifies that the guard is indeed protecting a variable that meets the criteria for The Guard Problem. We categorize a guard as ``Redundant'' if our tool determines that the variable does not require protection at that point (e.g., the variable is used later, or no GC trigger intervenes). Finally, we categorize a case as ``Missing'' if our tool detects the problematic pattern (derivation $\rightarrow$ trigger $\rightarrow$ usage) on a variable that is not protected by a guard.

\subsection*{Performance Impact of Excessive Guards}

One might argue that the simplest solution to The Guard Problem is to conservatively add \texttt{RB\_GC\_GUARD} to every \texttt{VALUE} variable. To evaluate the feasibility of this approach, we conducted a performance experiment. We instrumented the CRuby interpreter to apply \texttt{RB\_GC\_GUARD} to all \texttt{VALUE} variables in scope.

We then ran \texttt{ruby-bench}, the official benchmark suite maintained by the CRuby developers. The results showed a mixed performance impact. Specifically, we observed a geometric mean performance difference of -3.27\% across the benchmark suite. The maximum slowdown was 3.17\% observed in the 'fluentd' benchmark, while the minimum slowdown (speedup) was -7.60\% in the 'blurhash' benchmark. Figure \ref{fig:benchmark_comparison} details the results.

\begin{figure*}[t]
\centering
\includegraphics[width=0.75\textwidth]{benchmark_comparison.pdf}
\caption{Performance overhead of guarding all VALUEs relative to the original CRuby (positive values indicate slowdown).}
\label{fig:benchmark_comparison}
\end{figure*}

These results indicate that while the average runtime cost of guards may be low or even beneficial due to secondary effects (e.g., code layout changes), the performance impact is variable. More importantly, indiscriminate guarding obscures code intent and does not guarantee correctness if guards are placed incorrectly (e.g. too early). Thus, a precise static analysis tool like GuardLint is essential to ensure safety with minimal code intrusion.

\subsection*{Execution Time}
All queries complete within approximately 2 minutes on a standard laptop when analyzing the CRuby codebase. This execution time makes the approach feasible for continuous integration workflows, allowing automated analysis of code changes without significant impact on development velocity.

\section{Discussion}\label{sec:Discussion}

\subsection{CodeQL Capabilities}

CodeQL's relational database approach enabled systematic analysis of CRuby's codebase, processing complex control flow patterns within practical time constraints. The platform's declarative query language facilitated implementation of our temporal problematic code detection logic, allowing expression of the derivation-trigger-usage sequence through recursive predicates. 

\subsection{Case Study: OpenSSL Cipher Update}

To validate the ``Missing Guard'' results, we manually inspected the reported cases. One notable case was found in the \texttt{ossl\_cipher\_update} function within the OpenSSL extension.

Initially, we classified this report as a false positive. The variable in question, \texttt{data}, appeared to be safe because it was initialized via \texttt{rb\_scan\_args}, which typically anchors arguments on the stack. However, further inspection revealed a subtle bug. The code calls the \texttt{StringValue(data)} macro. If \texttt{data} is not already a String, this macro may create a new String object and assign it back to the \texttt{data} variable.

If the compiler optimizes the \texttt{data} variable away after this assignment, the pointer extracted from the new String object could become a dangling pointer if a GC occurs. We attempted to create a Proof of Concept (PoC) Ruby script to trigger a crash but were initially unsuccessful. 

Upon inspecting the compiled binary, we discovered that the compiler had not optimized the \texttt{data} variable away. We speculate this occurred because the address of \texttt{data} was passed to a function defined in a different translation unit. This likely acted as an optimization barrier, forcing the compiler to keep the variable in memory.

To verify the unsafety of the logic itself, we conducted a simulated experiment. We modified the C code to explicitly assign \texttt{Qnil} to \texttt{data} immediately after its last reference, simulating the effect of aggressive compiler optimization (register reuse). Under these simulated conditions, we successfully observed data corruption, confirming that the code logic is fundamentally unsafe and relies on implicit compiler behaviors for correctness.

\subsection{Analysis Precision Challenges}

While we successfully identified valid issues, determining the actual false positive rate requires extensive manual verification. The challenge is compounded by the need for a deep understanding of each code context to determine whether a guard is genuinely necessary or whether other factors (such as the translation unit boundary observed in the OpenSSL case) ensure safety.

\subsection{Future Work}

To make this analysis practical, future work must address the current limitations:

\textbf{Improved Precision}: Incorporating more sophisticated alias analysis and path-sensitive dataflow analysis could reduce false positives. Code understandings of Large Language Models (LLMs), as demonstrated in recent work~\cite{static_analysis_llm}, could help identify patterns that distinguish real bugs from benign code.

\textbf{Incremental Analysis}: Developing incremental analysis capabilities would make the tool more suitable for continuous integration, analyzing only changed code rather than the entire codebase.

\textbf{Practical Integration and Impact}: The ultimate goal of this work is to improve the code quality and security of the CRuby ecosystem. To achieve this, we plan to integrate the analysis tool into the CRuby development lifecycle. By running it automatically in a continuous integration (CI) environment, the tool could proactively flag potential issues in new pull requests, preventing regressions and systematically hardening the codebase against this class of memory safety bugs.

\section{Related Work}\label{sec:Related}

% \subsection{Static Analysis for Memory Safety}

Static analysis for memory safety has evolved significantly, with recent work addressing increasingly complex scenarios. Multiple approaches have been developed for detecting use-after-free bugs: Teodorescu and Lucanu~\cite{static_analysis_use_after_free_cpp} developed frameworks for detecting use-after-free bugs in C++, Yan et al.~\cite{spatio_temporal_context_reduction} introduced spatio-temporal context reduction techniques for scalable UAF detection in multi-MLOC C code, and Caballero et al.~\cite{static_analysis_dangling_pointer} proposed early detection of dangling pointers. Recent comparative studies~\cite{hassler2025comparativestudyfuzzersstatic} have evaluated both static analyzers and fuzzers for finding memory unsafety, showing that different tools discover different types of bugs. However, these approaches focus on traditional C/C++ memory management and do not address the unique challenges of garbage-collected language extensions where objects may be deallocated while extracted pointers remain in use.

Closest to our work is Ugawa and Fujimoto's study on detecting mistakes in registering local variables for precise garbage collection in an embedded JavaScript VM (eJSVM) using Coccinelle's control-flow–based pattern matching~\cite{UgawaFujimoto2019PRO}.
While our the problem is similar, in the case of \texttt{RB\_GC\_GUARD} we also have to track the subordinate pointer extraction operation and the usage of the extracted pointer. CFG‑only pattern matching (sufficient in their setting) is not enough here.


% \subsection{CodeQL and Query-Based Analysis}

Recent empirical evaluations have shown CodeQL's potential for security bug detection, with studies revealing it as the only tool capable of detecting certain bug categories ~\cite{charoenwet2024empirical}. CodeQL builds upon the foundational QL query language~\cite{ql_ecoop} to provide high-level analysis capabilities. Youn et al.~\cite{codeql_multilingual} extended CodeQL for multilingual program analysis, successfully tracking dataflows across Java-C and Python-C language boundaries.

%\subsection{Practical Static Analysis Tools}

Adam et al.~\cite{paralegal_static_analysis_privacy_bugs} developed Paralegal for privacy bug detection, emphasizing practical applicability and precision in real-world codebases. Their approach shares our emphasis on achieving manageable false positive rates while maintaining comprehensive coverage.

Li et al.~\cite{static_analysis_llm} improved static analysis precision using LLMs for bug detection in large codebases, showing the potential to improve analysis accuracy through advanced techniques.

\section{Conclusion}\label{sec:Conclusion}

We present a static analysis approach to detect missing \texttt{RB\_GC\_GUARD} directives in CRuby's C implementation using CodeQL. Our method identifies patterns where subordinate pointers may outlive their parent objects without proper protection, addressing a systematic source of memory safety issue with CRuby.

While our current implementation successfully identifies known problematic patterns, the discrepancy between flagged issues and confirmed bugs indicates that significant refinement is needed. The preliminary results demonstrate the feasibility of the approach but highlight the complexity of accurately modeling the interaction between conservative garbage collection and compiler optimizations.

Future work will focus on improving precision through better modeling of Ruby's internal safety mechanisms, implementing path-sensitive analysis, and extending coverage to handle Ruby 2.7+'s object movement features. Despite current limitations, this work represents an important step toward automated detection of a previously manual and error-prone aspect of CRuby development.
