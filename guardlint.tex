\title{GuardLint: Static Analysis of CRuby\\
for Checking GC Guards}

\affiliate{ISCT}{Institute of Science Tokyo,

\begin{abstract}
CRuby’s garbage collector (GC) conservatively scans the native stack to find object references. In C code, however, developers sometimes derive raw C pointers into object-owned buffers (e.g., via \texttt{RSTRING\_PTR}). Optimizing compilers may shorten the lifetime of the owning \texttt{VALUE} so that the object is no longer visible to conservative stack scanning, enabling use-after-free when GC runs. CRuby provides \texttt{RB\_GC\_GUARD} to extend \texttt{VALUE} liveness, but deciding where guards are needed is subtle; omissions can cause crashes while overuse adds noise and may affect performance.

We present GuardLint, a CodeQL-based static analyzer that flags likely missing \texttt{RB\_GC\_GUARD} sites. GuardLint identifies modeled derivations of derived pointers from \texttt{VALUE}s, over-approximates GC-triggering call sites using call-graph reachability (and conservative heuristics), and checks CFG ordering between derivation, trigger, and subsequent pointer uses while accounting for post-trigger \texttt{VALUE} accesses that tend to keep objects live.

On CRuby 3.4.5, GuardLint marks 32 existing guards as necessary under our model, reports 267 potentially redundant guards, and flags 236 candidate omissions. Manual inspection indicates that some reports depend on build configuration; for one OpenSSL-extension location we observed data corruption after simulating aggressive optimization that makes a \texttt{VALUE} non-rooted. A baseline that guards all \texttt{VALUE}s produced benchmark-dependent changes in our setup, including up to 3.17\% slowdown, motivating targeted checking.
\end{abstract}

\section{Introduction}
Many garbage-collected languages are implemented in unsafe languages such as C and C++. In such implementations, the runtime must ensure that the garbage collector can reliably discover all live objects even in the presence of compiler optimizations.

CRuby\footnote{\url{https://github.com/ruby/ruby}}, the reference implementation of Ruby, is written in C and uses conservative scanning of the native stack for GC roots. This design usually avoids explicit root registration, but it interacts poorly with optimized C code that derives raw pointers into object-owned memory (e.g., string byte buffers). If the compiler shortens the live range of the owning \texttt{VALUE}, a GC triggered by an intervening call may reclaim the object while the derived pointer is still in use, causing a use-after-free.

In CRuby, variables of type \texttt{VALUE} represent Ruby objects. CRuby’s GC discovers roots by scanning stack and machine-state locations where \texttt{VALUE}s may reside (e.g., registers / register save areas depending on platform and ABI). Optimizing compilers, however, can treat a variable as dead immediately after its last semantically observable use and can reuse its storage. This can make a Ruby object effectively invisible to conservative scanning even though the program still depends on memory reachable from that object via a derived pointer.

CRuby provides \texttt{RB\_GC\_GUARD} as an optimization barrier to force a \texttt{VALUE} to remain live at least until the guard site. Missing guards can cause crashes, but correct placement is challenging. Developers must reason about where derived pointers are produced, where GC might run, and whether the owning \texttt{VALUE} is still anchored when GC runs. We refer to this as \textbf{the Guard Problem}.

This paper presents GuardLint, a CodeQL-based static analysis to automatically flag likely missing \texttt{RB\_GC\_GUARD} calls and to highlight potentially redundant existing guards. GuardLint’s goal is to provide actionable locations for review rather than to prove absence of bugs.

The remainder of this paper is organized as follows. Section~\ref{sec:Background} provides background and characterizes the Guard Problem. Section~\ref{sec:Approach} describes our implementation. Section~\ref{sec:Experiment} reports analysis results on CRuby and discusses findings. Section~\ref{sec:Discussion} discusses capabilities and limitations. Section~\ref{sec:Related} reviews related work. Section~\ref{sec:Conclusion} concludes.

\section{Background}\label{sec:Background}
\subsection*{Subordinate (Object-Owned) Memory in CRuby}
Some Ruby objects own subordinate memory areas that are not themselves Ruby objects, such as a String’s byte buffer or an Array’s contiguous element storage. Such memory is allocated and reclaimed together with its owning object by the GC. A \emph{derived pointer} is a raw C pointer that points into such an area.

\subsection*{Accessing Subordinate Memory}
CRuby provides accessor macros such as \texttt{RSTRING\_PTR} and \texttt{RARRAY\_PTR} to obtain derived pointers:

\begin{figure}[tb]
\begin{lstlisting}[caption={Accessing object-owned memory}]
VALUE str = rb_str_new_cstr("Hello");
char *ptr = RSTRING_PTR(str);  // derived pointer
\end{lstlisting}
\end{figure}

Derived pointers remain valid only while their parent object lives. If a GC run reclaims the parent, the derived pointer becomes dangling.

\subsection{Compiler Optimizations and GC Safety}
CRuby’s GC is conservative with respect to the native stack: it identifies live objects by scanning the stack and other machine-state locations where \texttt{VALUE}s may reside. Optimizing compilers may shorten variable lifetimes and reuse storage locations once a \texttt{VALUE} is no longer needed from the language semantics point of view. This can break GC safety when code derives a raw pointer from a Ruby object and later uses that pointer after the original \texttt{VALUE} has become ``dead'' to the compiler.

Below are three common optimization families that contribute to the Guard Problem:

\subsubsection{Liveness Analysis and Register Allocation}
Compilers compute liveness and may treat a variable as dead immediately after its last observable use. In code like:
\texttt{VALUE v; const char *p = RSTRING\_PTR(v); /* ... */ use(p);}
the compiler may end \texttt{v}’s live range at the extraction point if \texttt{v} is not used again. The register allocator may then reuse the register, and \texttt{v} may not be materialized in memory across intervening calls. If GC runs while only \texttt{p} is in use, the object may no longer be discoverable as a root.

\subsubsection{Stack Slot Reuse (Stack Coloring / Stack Reuse)}
To reduce stack frame size, compilers may reuse stack slots for locals whose live ranges do not overlap.
For instance, GCC’s \texttt{-fstack-reuse} and LLVM’s stack coloring can repurpose a former \texttt{VALUE} slot for unrelated data once the compiler considers the \texttt{VALUE} dead. For a conservative collector, such reuse can make a live Ruby object invisible.

\subsubsection{Lifetime-Based Overlap and Spill/Store Elision}
Optimizers may avoid materializing a \texttt{VALUE} in memory at all, or eliminate/relocate stores to the stack when not required for semantics. In derived-pointer code, the last use of the \texttt{VALUE} may be considered earlier than the last use of the derived pointer, allowing overlap with later temporaries.

\subsubsection{The Mechanism of \texttt{RB\_GC\_GUARD}}
\texttt{RB\_GC\_GUARD(v)} is an optimization barrier that forces the compiler to keep \texttt{v} alive at least until the guard site. In CRuby, it is typically implemented by creating a \texttt{volatile VALUE *} pointing to \texttt{v} and issuing an empty inline assembly statement with a memory constraint, making the access appear as an observable side effect that must not be optimized away or reordered past the guard.

Crucially, \texttt{RB\_GC\_GUARD(v)} must be placed \emph{after} the last use of any derived pointer obtained from \texttt{v}; placing it earlier does not extend \texttt{v}’s live range to cover later derived-pointer uses.

\subsection*{Conservative Stack Scanning and the Guard}
CRuby uses conservative scanning for native-stack roots~\cite{ruby_conservative}. The simplified GNU-style implementation of \texttt{RB\_GC\_GUARD} in CRuby 3.4.5 is shown in Listing~\ref{lst:rbgcguard}.

\begin{figure}[tb]
\begin{lstlisting}[caption={RB\_GC\_GUARD (Simplified GNU-Style)},label={lst:rbgcguard}]
#ifdef __GNUC__
#define RB_GC_GUARD(v) \
    (*__extension__ ({ \
        volatile VALUE *rb_gc_guarded_ptr = &(v); \
        __asm__("" : : "m"(rb_gc_guarded_ptr)); \
        rb_gc_guarded_ptr; \
    }))
// ... (other compiler implementations omitted)
#endif
\end{lstlisting}
\end{figure}

\subsection{The Guard Problem}
We refer to the following pattern as the Guard Problem: code derives a pointer from a \texttt{VALUE}, executes a call that may trigger GC, and later uses the derived pointer while the owning \texttt{VALUE} may no longer be visible to conservative scanning.

\begin{figure}[tb]
\begin{lstlisting}[caption={The Guard Problem}]
VALUE str = rb_str_new_cstr("Hello");
char *ptr = RSTRING_PTR(str);
rb_ary_push(array, other_value); // may allocate / trigger GC
printf("%s\n", ptr);             // use after potential GC
\end{lstlisting}
\end{figure}

Manual \texttt{RB\_GC\_GUARD} placement is error-prone because developers must identify derivations, potential GC triggers, and the temporal coverage needed for the derived pointer’s lifetime. Moreover, GC may not run even when a trigger site is reached, making bugs hard to reproduce. Traditional static analyses for use-after-free in C/C++~\cite{static_analysis_use_after_free_cpp}\cite{spatio_temporal_context_reduction}\cite{static_analysis_dangling_pointer} do not directly address this conservative-GC setting.

\section{Approach}\label{sec:Approach}
We implemented GuardLint using CodeQL, a semantic code analysis engine that treats code as a queryable database. GuardLint is distributed as a small query pack\footnote{Artifact: \url{https://github.com/dummyx/guardql/tree/e8e4ed62f5ec89bd663ac380dccd2c933a48186d}. The main queries used in this paper are \texttt{missing\_guards\_vo.ql}, \texttt{redundant\_guards.ql}, and \texttt{good\_guards.ql} under \texttt{codeql-custom-queries-cpp}.}.

The implementation used for the results in Section~\ref{sec:Experiment} is primarily intraprocedural for derived-pointer usage. It over-approximates (a) where derived pointers are obtained, (b) which calls may trigger GC (via call-graph reachability and conservative heuristics), and (c) which operations constitute uses of a derived pointer (including passing it as an argument). GuardLint then reports sites matching the pattern \emph{derivation} $\rightarrow$ \emph{GC-triggering call} $\rightarrow$ \emph{pointer use}, when the owning \texttt{VALUE} is not anchored past the trigger by either a guard or a subsequent \texttt{VALUE}-level access.

\subsection{Modeling \texttt{VALUE}s, Derived Pointers, and Guards}
We identify variables of type \texttt{VALUE} as candidate owners of GC-managed objects. We also track C pointer-typed variables and expressions that may hold derived pointers into object-owned memory.

We model the protection mechanism \texttt{RB\_GC\_GUARD}. Since it is a macro, GuardLint detects it via a characteristic expansion pattern in the GNU-style implementation used by CRuby: the introduction of a local temporary named \texttt{rb\_gc\_guarded\_ptr} initialized with the address of the guarded \texttt{VALUE}. This detection is lightweight but implementation-dependent: alternative compiler implementations or manually inlined equivalents may not be recognized, potentially causing false negatives.

\subsection{Tracking Pointer Derivation}
The core hazard arises when a raw pointer is derived from a \texttt{VALUE}. GuardLint models derivations by recognizing common CRuby access patterns (e.g., accessor macros and helper functions) that return pointers to object-owned memory. A derivation site is recorded when the derived pointer value is assigned to a pointer variable or otherwise captured for later use.

This is necessarily an over-approximation: not all recognized APIs always produce unsafe pointers, and some unsafe derivations may be missed if they are not covered by the modeled set.

\subsection{GC Trigger Over-Approximation}
To identify calls that may trigger GC, GuardLint computes a transitive closure over the call graph starting from the GC entry point \texttt{gc\_enter} and marks call sites that may reach those entry points. 

\subsection{Ordering and Liveness Approximation}
GuardLint’s central predicate (\texttt{needsGuard}) captures the temporal pattern:
\[
\text{Derivation} \xrightarrow{CFG+} \text{Trigger} \xrightarrow{CFG+} \text{Use}.
\]
A report is generated when (i) a derived pointer is used after a modeled trigger site and (ii) the owning \texttt{VALUE} is not accessed after the trigger (which often forces the compiler to keep it live) and is not protected by a detected \texttt{RB\_GC\_GUARD}.

For calls, GuardLint conservatively treats passing a derived pointer as an argument as a potential use (since the callee may dereference it), but it does not fully analyze derived-pointer dereferences inside callees in the configuration used for this paper.

\section{Experiment}\label{sec:Experiment}
We evaluated GuardLint on CRuby codebase tagged \texttt{v3\_4\_5}, which contains 339,617 lines of C code as measured by \texttt{scc}\footnote{\url{https://github.com/boyter/scc}}.

\subsection*{Classification of Results}
We compare GuardLint’s judgments with existing \texttt{RB\_GC\_GUARD} placements in the codebase as a reference point. We classify an existing guard as \emph{Matched} if the guarded variable satisfies our \texttt{needsGuard} predicate at that program point. We classify it as \emph{Potentially redundant} if the variable does not satisfy \texttt{needsGuard} there (e.g., there is no modeled GC trigger on relevant paths, or the variable is accessed after the trigger). Finally, we report a \emph{Missing} site when a variable satisfies \texttt{needsGuard} but is not detected as guarded.

\subsection*{Performance Impact of Blanket Guarding}
A naive strategy is to add \texttt{RB\_GC\_GUARD} to every \texttt{VALUE} variable. To assess practicality, we instrumented CRuby to apply \texttt{RB\_GC\_GUARD} broadly and ran \texttt{ruby-bench}, the benchmark suite used by CRuby developers.

We observed benchmark-dependent effects. In our setup, the geometric mean performance difference was -3.27\% across the suite (negative indicates speedup), with a maximum slowdown of 3.17\% in the \texttt{fluentd} benchmark and a maximum speedup of -7.60\% in \texttt{blurhash}. Figure~\ref{fig:benchmark_comparison} summarizes the results.

\begin{figure}[h]
\centering

\caption{Performance change from guarding all VALUEs relative to the original CRuby (positive values indicate slowdown).}

These results suggest that indiscriminate guarding can change performance in non-uniform ways and adds code clutter. More importantly, blanket guarding does not guarantee correctness if guards are placed too early. This motivates a tool that helps focus review on likely omission sites and highlights candidates for cleanup.

\subsection*{Execution Time}
In our preliminary runs, the queries completed within a few minutes on laptop-class hardware. The exact timing depends on CodeQL version, database build settings, and hardware; nevertheless, the runtime suggests feasibility for iterative use and potential CI integration.

\section{Discussion}\label{sec:Discussion}

\subsection{What GuardLint Can Express Well}
CodeQL’s relational representation of code makes it convenient to express patterns involving calls, control flow reachability, and API usage. GuardLint benefits from (i) explicit modeling of derivation sites and (ii) CFG reachability checks for the derivation--trigger--use sequence.

\subsection{Case Study: OpenSSL Cipher Update}
We manually inspected representative ``Missing'' reports. One notable case appears in \texttt{ossl\_cipher\_update} in the OpenSSL extension. The pattern involves converting an argument with \texttt{StringValue(data)}, extracting a derived pointer from the resulting String, and then executing operations that may trigger GC before the derived pointer is fully consumed.

We did not reproduce a crash in a standard build configuration; in that setup, the compiler did not eliminate or overwrite the \texttt{data} \texttt{VALUE} in a way that makes it invisible to conservative scanning. However, the code pattern can become unsafe if the compiler shortens the live range of \texttt{data} after its last \texttt{VALUE}-level use.

To probe this brittleness, we performed a simulated experiment by explicitly assigning \texttt{Qnil} to \texttt{data} immediately after its last \texttt{VALUE}-level use, approximating an aggressive optimization that removes the root. Under this modification we observed data corruption, indicating that the code can rely on implicit compiler behavior for safety. This result does not by itself demonstrate an exploitable bug in shipping builds, but it motivates closer review and more robust anchoring where appropriate.

\subsection{Limitations and Threats to Validity}
GuardLint’s results are candidates for review rather than definitive proofs of unsafety. Key limitations include:
\begin{itemize}
  \item \textbf{GC trigger over-approximation:} Call-graph reachability and callback heuristics can over-report triggers, increasing false positives.
  \item \textbf{Guard detection dependence on macro expansion:} Our recognition of \texttt{RB\_GC\_GUARD} is tied to a particular expansion pattern; alternative implementations may be missed.
  \item \textbf{Primarily intraprocedural reasoning:} Derived-pointer uses inside callees are conservatively approximated (e.g., by treating argument passing as a use), which can both miss and over-report certain patterns.
  \item \textbf{Build-configuration sensitivity:} Whether a missing guard is practically exploitable depends on compiler, flags, LTO, ABI, and inlining decisions.
\end{itemize}

\subsection{Future Work}
Improving precision likely requires better aliasing and path sensitivity, more robust modeling of safe APIs, and explicit handling of common ``implicit anchoring'' idioms. A validated interprocedural analysis of derived-pointer use inside callees would expand coverage for helper-function patterns and callbacks. Finally, packaging GuardLint for CI (with incremental analysis) would enable continuous feedback to developers.

\section{Related Work}\label{sec:Related}
Static analysis for memory safety has evolved significantly, with recent work addressing increasingly complex scenarios. Multiple approaches have been developed for detecting use-after-free bugs: Teodorescu and Lucanu~\cite{static_analysis_use_after_free_cpp} developed frameworks for detecting use-after-free bugs in C++, Yan et al.~\cite{spatio_temporal_context_reduction} introduced spatio-temporal context reduction techniques for scalable UAF detection in multi-MLOC C code, and Caballero et al.~\cite{static_analysis_dangling_pointer} proposed early detection of dangling pointers. Recent comparative studies~\cite{hassler2025comparativestudyfuzzersstatic} evaluate both static analyzers and fuzzers for finding memory unsafety, showing complementarity across tools. These approaches largely focus on explicit memory management rather than conservative-GC settings where derived pointers can outlive visible roots.

Closest to our work is Ugawa and Fujimoto's study on detecting mistakes in registering local variables for precise garbage collection in an embedded JavaScript VM (eJSVM) using Coccinelle's control-flow--based pattern matching~\cite{UgawaFujimoto2019PRO}. While the setting is similar, in the case of \texttt{RB\_GC\_GUARD} we must track both derived-pointer extraction and derived-pointer usage, and we must reason about the absence of \texttt{VALUE}-level accesses after potential trigger points.

Empirical evaluations have shown CodeQL's potential for security bug detection, with studies revealing it can detect bug categories missed by other tools~\cite{charoenwet2024empirical}. CodeQL builds upon the foundational QL language~\cite{ql_ecoop} to provide high-level analysis capabilities. Youn et al.~\cite{codeql_multilingual} extended CodeQL for multilingual program analysis, tracking dataflows across language boundaries.

\section{Conclusion}\label{sec:Conclusion}
We presented GuardLint, a CodeQL-based analysis that flags likely missing \texttt{RB\_GC\_GUARD} directives in CRuby’s C code. GuardLint identifies patterns where derived pointers into object-owned memory may outlive the visibility of their owning \texttt{VALUE} across GC-triggering calls, which can lead to use-after-free under certain compiler optimizations.

On CRuby 3.4.5, GuardLint reported 236 candidate omissions, 267 potentially redundant guards, and 32 existing guards that appear necessary under our model. While some reports depend on build configuration and conservative modeling choices, the results demonstrate that query-based static analysis can systematically surface locations that merit review.

Future work will focus on improving precision through stronger modeling of safe APIs and anchoring idioms, more robust guard detection across compiler implementations, and deeper interprocedural analysis. Ultimately, integrating GuardLint into CI workflows could help prevent regressions and improve the robustness of the CRuby ecosystem against this class of memory safety bugs.
