\section{Introduction}
Many programming languages with automatic memory management (so-called \emph{garbage-collected languages}) are implemented in unsafe languages such as C and C++. Those implementations have to carefully manipulate the pointers so that garbage collectors correctly recognize used and unused memory areas.

% \todo[inline]{fix problem definition}
CRuby\footnote{\url{https://github.com/ruby/ruby}}, which is the most widely used Ruby implementation, is implemented in C. CRuby requires its implementation to add a macro called \texttt{RB\_GC\_GUARD} under a certain condition that ensures validity of the pointers. However, it is easy to forget to insert the guard macro calls, which in fact resulted in many memory bugs. The authors believe that there are still many uncovered bugs.% the  and has the dangling pointer problem. That is, when a Ruby object's memory area is collected by the garbage collector, the pointers pointing to subordinate memory areas of the object become dangling pointers, which, if accessed again, will cause the interpreter to crash (segmentation fault).

In the CRuby implementation, including both the interpreter core and its C extensions, variables of type \texttt{VALUE} to represent Ruby objects. CRuby's conservative garbage collector~\cite{gchandbook} does not require the implementation to explicitly inform the object references of the GC since it automatically takes the C stack and the registers as GC root. Compiler optimizations can overwrite the registers that references Ruby objects after the last use. This causes the GC to reclaim objects that still look to be referenced by a variable at the source code level. A critical memory bug arises when the C code extracts a pointer to a subordinate memory area of an object. A subordinate memory area is raw C memory area owned by a Ruby object but not itself a Ruby object. For example, a String's byte buffer or an Array's contiguous element storage. This memory is allocated and reclaimed together with its owning object by the garbage collector. And a subordinate pointer is a raw C pointer that points into such an area, typically obtained via accessor macros such as \texttt{RSTRING\_PTR} or \texttt{RARRAY\_PTR}. The garbage collector deallocates the object while extracted pointer remains in use, which means a use-after-free bug.

CRuby provides a macro named \texttt{RB\_GC\_GUARD} to ensure that \texttt{VALUE} variables remain on the stack, preventing them from being prematurely collected.  

Missing guards cause crashes. But correct placement is challenging. Developers must identify where extracted pointers might be accessed after garbage collection triggers, which we call \textbf{The Guard Problem}.

\section{Background}\label{sec:Background}
\subsection*{Memory Organization in CRuby}

In CRuby, some objects have a subordinate memory area which is a non-Ruby object data, retrieved by a pointer from a Ruby object, and becomes invalid when the parent object is reclaimed by the garbage collector. For instance, the body of a String object is a subordinate memroy area, as it is allocated outside of the object heap and is deallocated when the string object is garbage collected. 

\subsection*{Accessing Subordinate Memory}

CRuby provides accessor macros such as \texttt{RSTRING\_PTR} and \texttt{RARRAY\_PTR} to extract raw C pointers to these subordinate areas:

\begin{lstlisting}[language=C,basicstyle=\footnotesize\ttfamily]
VALUE str = rb_str_new_cstr("Hello");
char *ptr = RSTRING_PTR(str);  
// extract pointer to string data
\end{lstlisting}

Subordinate pointers remain valid only while their parent object lives. If the garbage collector determines the parent is unreachable, it deallocates both the object and its subordinate memory, leaving any extracted pointers dangling. The critical requirement is that parent objects must remain reachable throughout subordinate pointer usage.

\subsection*{Compiler Optimizations}

C compilers may allocate a C variable to a register and reuse the register for another variable when the first variable is no longer accessed. For example, in the following code fragment, compiled code of the str would be allocated in register, and then another variable may be allocated in the same register at line 5.

\begin{lstlisting}[language=C,basicstyle=\footnotesize\ttfamily]
VALUE str = rb_str_new_cstr("data");
char *ptr = RSTRING_PTR(str);
// Compiler may eliminate str
// from stack/registers here
VALUE new_str = rb_str_new_cstr("new data");
process_data(ptr);  
// str invisible to GC
\end{lstlisting}

This optimization is valid from the C perspective but does not cooperate well with CRuby's conservative garbage collector, which relies on scanning the stack and registers to find live objects. When the compiler overwrites a register that store an object reference, the GC cannot detect that the object is still needed for accessing its subordinate pointers.

\subsection*{Conservative GC and the Guard}

CRuby uses a conservative garbage collector~\cite{ruby_conservative} which identifies live objects by scanning the C stack and registers. To prevent compiler optimizations from overwriting registers, CRuby provides the \texttt{RB\_GC\_GUARD} macro, which creates a volatile reference ensuring that the variable remains visible to the garbage collector. The implementation of the macro in CRuby version 3.4.5 is listed in Listing 1.

\begin{figure*}[t]
\begin{lstlisting}[language=C,basicstyle=\footnotesize\ttfamily,breaklines=true,caption=RB\_GC\_GUARD's definition]
#ifdef __GNUC__
#define RB_GC_GUARD(v) \
    (*__extension__ ({ \
        volatile VALUE *rb_gc_guarded_ptr = &(v); \
        __asm__("" : : "m"(rb_gc_guarded_ptr)); \
        rb_gc_guarded_ptr; \
    }))
#elif defined _MSC_VER
#define RB_GC_GUARD(v) (*rb_gc_guarded_ptr(&(v)))
#else
#define HAVE_RB_GC_GUARDED_PTR_VAL 1
#define RB_GC_GUARD(v) (*rb_gc_guarded_ptr_val(&(v),(v)))
#endif
\end{lstlisting}
%\caption{RB\_GC\_GUARD's definition}
\label{lst:rbgcguard}
\end{figure*}

\subsection{The Guard Problem}

We identify a specific class of memory safety problem in CRuby's C implementation that we term \textbf{The Guard Problem}. This occurs when the C code uses a pointer that points to a subordinate memory area within garbage-collected objects.

Consider this code fragment:
\begin{lstlisting}[language=C,basicstyle=\footnotesize\ttfamily]
VALUE str = rb_str_new_cstr("Hello");
char *ptr = RSTRING_PTR(str);
rb_ary_push(array, other_value);
printf("%s\n", ptr);
\end{lstlisting}

The compiler may allocate str in a register and overwrites the register by another local variable before executing line 3. Because the String object is not referenced from any registers or the stack, and when GC runs inside of rb\_ary\_pysh, the String object is reclaimed.

Manual \texttt{RB\_GC\_GUARD} placement is error-prone because developers must (1) identify all locations where subordinate pointers are extracted, (2) locate potential GC trigger points, (3) ensure guards cover the entire lifetime of pointer usage. The complexity of the condition when the guard is needed and the subtlety of GC make this a frequent source of bugs. Furthermore, as GC will not start a lot of the time when a GC trigger is called, it is hard to reproduce and debug this kind of bug. Although there are static analysis frameworks for detecting use-after-free bugs in traditional C++~\cite{static_analysis_use_after_free_cpp}\cite{spatio_temporal_context_reduction}\cite{static_analysis_dangling_pointer}, The Guard Problem presents unique challenges specific to conservative garbage collection environments.

\section{Approach}\label{sec:Approach}

\subsection{CodeQL for Static Analysis}

CodeQL is a code analysis platform that derivates source code into a relational database representation. CodeQL uses QL, a declarative query language based on Datalog, to express program analysis logic through predicates and recursive queries.

CodeQL's database derivation captures semantic information including abstract syntax trees, control flow graphs, data flow relationships, and type hierarchies. This supports interprocedural analysis for tracking VALUE objects and their derivated pointers across function boundaries in CRuby's C codebase.

\begin{lstlisting}[basicstyle=\scriptsize\ttfamily]
predicate isGcTrigger(Function function) {
  exists(Expr s, Call call |
    s.getEnclosingFunction() = function and
    s.getAChild*() = call and
    (call.getTarget().getName() = "gc_enter" 
      or isGcTrigger(call.getTarget()))
  )
}
\end{lstlisting}

\subsection{Static Analysis Approach Overview}
We model the main problematic patterns and implement both intraprocedural and interprocedural analysis to track pointer lifetimes across function boundaries.

\subsection{Problematic Pattern Classification}

Our analysis detects problematic patterns across different syntactic forms of pointer derivation:

\textbf{Declaration Pattern}: Pointer derivation during variable declaration:
\begin{lstlisting}[language=C,basicstyle=\tiny\ttfamily]  
// time.c
// static wideval_t extract_time(VALUE time)
// ...
if (rb_typeddata_is_kind_of(time, &time_data_type)) {
    struct time_object *tobj = RTYPEDDATA_GET_DATA(time);

    time_gmtime(time); /* ensure tm got */
    t = rb_time_unmagnify(tobj->timew);

    RB_GC_GUARD(time);
}
// ...
\end{lstlisting}

\textbf{Initialized Later Pattern}: Pointer is initialized after declaration:
\begin{lstlisting}[language=C,basicstyle=\tiny\ttfamily]
// file.c
rb_freopen(VALUE fname, const char *mode, FILE *file)
{
    WCHAR *wname, wmode[4];
    VALUE wtmp;
    char *name;
    long len;
    int e = 0, n = MultiByteToWideChar(
                     CP_ACP, 0, mode, -1, NULL, 0);
    if (n > numberof(wmode)) return EINVAL;
    MultiByteToWideChar(
      CP_ACP, 0, mode, -1, wmode, numberof(wmode));
    RSTRING_GETMEM(fname, name, len);
    n = rb_long2int(len);
    len = MultiByteToWideChar(CP_UTF8, 0, name, n, NULL, 0);
    wname = ALLOCV_N(WCHAR, wtmp, len + 1);
    len = MultiByteToWideChar(CP_UTF8, 0, name, n, wname, len);
    wname[len] = L'\0';
    RB_GC_GUARD(fname);
    // ...
}
\end{lstlisting}


\textbf{Interprocedural Pattern}: Derivated pointers passed to functions that may trigger GC:
\begin{lstlisting}[language=C,basicstyle=\tiny\ttfamily]
// digest.c
static VALUE
rb_digest_base_update(VALUE self, VALUE str)
{
    rb_digest_metadata_t *algo;
    void *pctx;

    algo = get_digest_obj_metadata(self);

    TypedData_Get_Struct(self, void, &digest_type, pctx);

    StringValue(str);
    algo->update_func(pctx, 
        (unsigned char *)RSTRING_PTR(str), RSTRING_LEN(str));
    RB_GC_GUARD(str);

    return self;
}
\end{lstlisting}

\subsection{GC Trigger Detection}

We implement recursive call analysis to detect both direct and indirect GC triggers. It is done by analyze the call graph to identify functions that eventually call GC entry points.

\subsection{Interprocedural Pointer Usage Analysis}

We implement an \texttt{isArgumentNotSafe} predicate that performs interprocedural analysis to determine if  function arguments might be used unsafely. 

\subsection{Control-flow Analysis}

Control-flow analysis is essential for matching the problematic code pattern where derivated pointers are used after GC triggers. Our approach must verify that pointer derivation precedes GC triggers, which precede pointer usage, along feasible execution paths.

CodeQL's control flow graph (CFG) analysis enables determination of operation ordering to detect code matching the following execution order:

1. A certain \texttt{VALUE} variable's last reference
2. GC triggers
3. Usage of pointers pointing to the subordinate memory area

\section{Discussion}\label{sec:Discussion}

\subsection{CodeQL Capabilities}

CodeQL's relational database approach enabled systematic analysis of CRuby's codebase, processing complex control flow patterns within practical time constraints. The platform's declarative query language facilitated implementation of our temporal problematic code detection logic, allowing expression of the derivation-trigger-usage sequence through recursive predicates. 

However, the logic programming paradigm presents debugging challenges. Unlike imperative approaches where execution flow can be traced step-by-step, CodeQL's declarative nature makes it difficult to understand why certain results are included or excluded. The lack of intermediate state visibility and the recursive nature of many predicates complicate the process of refining queries to reduce false positives. Additionally, distinguishing between syntactically similar but semantically different code patterns requires domain knowledge that is challenging to encode in purely structural queries.

\subsection{Analysis Precision Challenges}

The analysis reveals a significant discrepancy between variables requiring protection (5,875) and those currently guarded (297). No comprehensive verification has been conducted yet, but the high number of detected cases indicates that either there are likely substantial false positives, or potential widespread of \texttt{RB\_GC\_GUARD} related bugs. Despite these limitations, our approach successfully detected the missing \texttt{RB\_GC\_GUARD} issue that was subsequently fixed in \texttt{vm\_backtrace.c} \footnote{\url{https://bugs.ruby-lang.org/projects/ruby-master/repository/git/revisions/fd59ac6410d0cc93a8baaa42df77491abdb2e9b6}}, demonstrating the potential of the method with further refinement.

The successful detection of the missing of guard in \texttt{vm\_backtrace.c} demonstrates that legitimate issues exist within the flagged results. However, determining the actual false positive rate requires extensive manual verification that was infeasible within this study's scope. The challenge is compounded by the need for deep understanding of each code context to determine whether a guard is genuinely necessary or whether other factors ensure safety.

\subsection{Future Work}

To make this analysis practical, future work must address the current limitations:

\textbf{Improved Precision}: Incorporating more sophisticated alias analysis and path-sensitive dataflow analysis could reduce false positives. Code understandings of Large Language Models (LLMs), as demonstrated in recent work~\cite{static_analysis_llm}, could help identify patterns that distinguish real bugs from benign code.

\textbf{Incremental Analysis}: Developing incremental analysis capabilities would make the tool more suitable for continuous integration, analyzing only changed code rather than the entire codebase.

\textbf{Practical Integration and Impact}: The ultimate goal of this work is to improve the code quality and security of the CRuby ecosystem. To achieve this, we plan to integrate the analysis tool into the CRuby development lifecycle. By running it automatically in a continuous integration (CI) environment, the tool could proactively flag potential issues in new pull requests, preventing regressions and systematically hardening the codebase against this class of memory safety bugs.

\section{Related Work}\label{sec:Related}

% \subsection{Static Analysis for Memory Safety}

Static analysis for memory safety has evolved significantly, with recent work addressing increasingly complex scenarios. Multiple approaches have been developed for detecting use-after-free bugs: Teodorescu and Lucanu~\cite{static_analysis_use_after_free_cpp} developed frameworks for detecting use-after-free bugs in C++, Yan et al.~\cite{spatio_temporal_context_reduction} introduced spatio-temporal context reduction techniques for scalable UAF detection in multi-MLOC C code, and Caballero et al.~\cite{static_analysis_dangling_pointer} proposed early detection of dangling pointers. Recent comparative studies~\cite{hassler2025comparativestudyfuzzersstatic} have evaluated both static analyzers and fuzzers for finding memory unsafety, showing that different tools discover different types of bugs. However, these approaches focus on traditional C/C++ memory management and do not address the unique challenges of garbage-collected language extensions where objects may be deallocated while extracted pointers remain in use.

Closest to our work is Ugawa and Fujimoto's study on detecting mistakes in registering local variables for precise garbage collection in an embedded JavaScript VM (eJSVM) using Coccinelle's control-flow–based pattern matching~\cite{UgawaFujimoto2019PRO}.
While our the problem is similar, in the case of \texttt{RB\_GC\_GUARD} we also have to track the subordinate pointer extraction operation and the usage of the extracted pointer. CFG‑only pattern matching (sufficient in their setting) is not enough here.


% \subsection{CodeQL and Query-Based Analysis}

Recent empirical evaluations have shown CodeQL's potential for security vulnerability detection, with studies revealing it as the only tool capable of detecting certain vulnerability categories ~\cite{charoenwet2024empirical}. CodeQL builds upon the foundational QL query language~\cite{ql_ecoop} to provide high-level analysis capabilities. Youn et al.~\cite{codeql_multilingual} extended CodeQL for multilingual program analysis, successfully tracking dataflows across Java-C and Python-C language boundaries.

%\subsection{Practical Static Analysis Tools}

Adam et al.~\cite{paralegal_static_analysis_privacy_bugs} developed Paralegal for privacy bug detection, emphasizing practical applicability and precision in real-world codebases. Their approach shares our emphasis on achieving manageable false positive rates while maintaining comprehensive coverage.

Li et al.~\cite{static_analysis_llm} improved static analysis precision using LLMs for bug detection in large codebases, showing the potential to improve analysis accuracy through advanced techniques.

\section{Conclusion}\label{sec:Conclusion}

We present a static analysis approach to detect missing \texttt{RB\_GC\_GUARD} directives in CRuby's C implementation using CodeQL. Our method identifies patterns where subordinate pointers may outlive their parent objects without proper protection, addressing a systematic source of memory safety issue with CRuby.

While our current implementation successfully identifies known problematic patterns, the high false positive rate indicates that significant refinement is needed before the tool can be deployed in production environments. The preliminary results demonstrate the feasibility of the approach but highlight the complexity of accurately modeling the interaction between conservative garbage collection and compiler optimizations.

Future work will focus on improving precision through better modeling of Ruby's internal safety mechanisms, implementing path-sensitive analysis, and extending coverage to handle Ruby 2.7+'s object movement features. Despite current limitations, this work represents an important step toward automated detection of a previously manual and error-prone aspect of CRuby development.
